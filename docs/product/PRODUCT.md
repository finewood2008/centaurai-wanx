# 万象产品基线 · Draft 0.1

日期：2026-08-30
状态：待共同评审
产品定义：社群陪跑的工作 Agent Builder

## 1. 产品判断

普通人很难独自把真实需求完整表达成一个可靠的软件系统。把创建过程压缩成一句话，只会隐藏需求澄清、数据理解、异常处理、权限、安全和验收等必要工作，最终更容易得到一次性演示，而不是可以长期使用的应用。

万象不把“无需学习、无需协作、立即生成”作为目标。需求发现、构建、验证、运行和维护都发生在同一个万象工作台中；底层开放 Agent 内核是内部实现，不形成第二套产品。万象 Builder Agent 与成员共同完成真实工作，社群作为外部支持服务提供咨询、反馈与课程，但不参与阶段解锁或验收判断。

## 2. 核心承诺

万象交付的不是一个页面或一段代码，而是一个经过真实工作验证的能力：

1. 能连接成员被授权使用的真实数据。
2. 能完成一个边界明确、可重复发生的工作任务。
3. 能解释它做了什么，并保留可回放证据。
4. 在高风险动作前获得人的批准。
5. 能通过测试、版本和反馈持续改进。

## 3. 用户与角色

### 社群成员（Creator）

拥有具体工作问题和领域知识，但不要求具备软件工程能力。成员负责描述工作现实、提供样例、判断结果是否有用，并逐步学会维护自己的 Agent。

### 社群支持（External Service）

通过产品内的侧边抽屉提供问题咨询、产品反馈、课程与同伴交流。社群不进入 Builder 流程，不承担范围确认、验收或发布批准；项目成员仍是工作判断与结果验收的责任人。

### 万象 Builder Agent

在万象工作台中运行的构建 Agent。它负责访谈、工作流建模、连接 Data Agent、生成配置与能力、建立评测、组织试运行，并在每个阶段解释为什么需要这些工作。

### 平台运营者（Operator）

维护模板、权限策略、运行时版本兼容、Data Agent 接口、社群课程和交付质量。

## 4. 核心产品闭环

### 发现真实工作

成员带来一个最近真实发生过的任务，而不是抽象的产品想法。Builder Agent 通过多轮对话逐项确认目标、输入、判断规则、输出、风险边界和验收标准：每轮只追问一个主题，提供可选项并始终允许自由回答；右侧工作简报随对话实时累积，最后由成员通读确认。

产物：`Work Brief`，包含一个真实案例和明确边界。

### 定义工作与数据

Builder Agent 将工作拆成可观察步骤，通过万象 Data Agent Bridge 查看可用数据能力，并按最小权限建立读取或写入连接。

产物：工作流、数据契约、权限声明和风险清单。

### 在万象工作台中构建与验证

确认定义后，产品在同一个界面原位进入自由工作台。Builder Agent 在当前项目会话中组合所需 Skills、Tools、Goals 和 Workflows，并立即用历史案例和边界案例验证；发现问题就继续修改，不再把“构建”和“验证”拆成两个交接阶段。

产物：可执行 Agent、验收集、失败处理和运行说明。

### 使用与持续改进

Agent 在万象中处理真实任务，但暂不自动执行高风险写操作。成员将结果与自己的原做法对比，标记正确、需修改或不可接受；每次改动都回到同一个构建验证循环。

产物：真实运行证据、质量基线和批准边界。

达到门槛后形成可回滚版本，继续在万象会话中查看运行、批准关键动作和维护能力；需要帮助时从侧边栏的社群抽屉进入外部支持服务。

产物：真实运行证据、可回滚版本、操作记录和下一轮改进目标。

## 5. “有用”的最低定义

一个万象应用只有同时满足以下条件，才算完成，而不是玩具：

- 面向一项真实且会重复发生的工作。
- 至少使用一个经授权的真实数据源，或明确验证真实输入。
- 用不少于 5 个代表性案例完成验收，其中至少 2 个是异常或边界案例。
- 连续完成 3 次真实运行，结果由成员确认可接受。
- 所有外部写入、发送、删除、付款等高风险动作都有明确批准策略。
- 运行过程可追溯，失败时能说明下一步，而不是静默结束。
- 成员知道如何启动、停止、检查和反馈该 Agent。

## 6. 目标与非目标

### 第一阶段目标

- 证明社群陪跑可以把普通成员的工作问题稳定转化为可靠 Agent。
- 建立一套从工作发现到真实运行的共同语言和交付门槛。
- 形成万象 Builder Agent、Data Agent Bridge 和成员验收机制的最小闭环。
- 让完成者具备基本维护能力，而不是永久依赖平台代做。

### 当前非目标

- 不承诺“一句话生成任意应用”。
- 不优先建设拖拽式页面编辑器或庞大的模板市场。
- 不另建一套外置引导产品，也不让用户在多个工作台之间跳转。
- 不在 MVP 同时覆盖所有职业和所有数据源。
- 不把页面美观、代码量或创建数量作为主要成功指标。

## 7. MVP

首个 Cohort 建议选择 10–20 名社群成员，并聚焦 1–2 类相邻工作场景。每位成员只完成一个高频、低到中等风险、结果可判断的工作流。

MVP 包含：

- 万象独立本地运行时与固定版本兼容层。
- 四段式体验：发现、定义、构建验证、使用；全部在同一个万象工作台中完成。
- Data Agent Bridge 的能力发现、只读查询和审批式写入。
- 项目工作区、真实案例、评测集、版本与运行日志。
- 万象原生主工作界面和流程外的社群支持抽屉。
- 影子运行、人工批准、失败说明和回滚。

MVP 暂不包含：

- 无人值守的高风险自动化。
- 公共 Agent 市场。
- 面向匿名用户的完全自助 onboarding。
- 复杂多人协同编辑和企业级组织管理。

## 8. 成功指标

| 指标 | Draft 目标 | 如何测量 |
|---|---:|---|
| 首次真实价值时间 | 14 天内 | 入组到首次通过验收的真实运行 |
| Cohort 交付率 | ≥ 60% | 入组成员中达到“有用”最低定义的比例 |
| 4 周持续使用率 | ≥ 50% | 已交付 Agent 在第 4 周仍完成有效运行 |
| 已批准运行成功率 | ≥ 90% | 输出被接受且未触发严重返工的运行比例 |
| 高风险动作受控率 | 100% | 需要批准的动作均记录批准或拒绝 |
| 可追溯率 | 100% | 每次正式运行均能回放输入、工具调用和结果 |
| 成员可维护率 | ≥ 70% | 成员能独立完成一次小修改并通过回归验收 |

## 9. 产品原则

1. **真实工作先于产品想法。** 从最近发生过的任务开始。
2. **证据先于完成动画。** 没有真实运行和验收，就没有完成。
3. **引导构建先于一步生成。** Builder 负责解释过程，成员负责工作判断；社群支持独立于产品流程。
4. **逐步揭示复杂度。** 不隐藏必要概念，也不提前倾倒全部工程术语。
5. **默认保留人的判断。** 自动化范围随证据逐步扩大。
6. **可维护比首次生成更重要。** 每个 Agent 都必须有版本、测试和说明。
7. **只有万象，不暴露内部实现。** 用户学习的是自己的工作 Agent 如何运行，而不是底层框架术语。

## 10. 需要共同决定的问题

- 首个 Cohort 聚焦哪一类成员和哪两类工作场景？
- Data Agent 当前已经提供哪些读取、写入、权限和审计接口？
- MVP 以成员本地运行、社群托管运行，还是混合模式为主？
- 社群支持服务采用什么响应机制，如何把高频问题沉淀为课程与 Builder 指引？
- “成员可维护”需要掌握到什么程度：修改指令、调整工作流，还是能增加工具？
