# 万象产品基线 · v0.4

日期：2026-09-02
状态：设计已批准，第 0 期实施中
产品定义：让 IT 能力很弱的社会精英，通过万象这个 agent 打造自己趁手的 AI 助理

## 1. 用户与产物

目标用户是半人马社群成员：表达力强、判断力强、时间少、对隐私敏感、有真实工作与
真实数据，但不装软件、不配 key、不看终端。他们熟悉的心智模型是秘书、外包、合伙人。

万象造出来的「应用」是一个有名字、可反复运行的 agent 助理：说明书（人格 + 工作手册）、
资料与数据连接、产出格式、运行方式（手动 / 定时 / 触发）、边界与审批、验收案例、
版本史。它是可导出、可分享、可 fork 的应用包；不是一段代码，不是一个网页。

## 2. 已拍板的前提

- **D1 交付形态：社群托管，一人一容器。** 成员零安装、零 key，收到链接即用。
- **D2 产物：可反复运行的 agent 助理。** 不生成网页或代码类产品。
- **D3 远程支持最深一档：工作人员可接管对话。** 成员实时看到、随时收回。
- **D4 分享默认只带说明书，案例逐条勾选。**
- **术语归零。** 界面只用七个词：应用、说明书、资料、运行、产出、版本、审批。

## 3. 三条设计铁律（来自 DSH 代码事实）

1. DSH 是单用户本机引擎。用户、鉴权、支持授权、分享全部在万象层做；DSH 只当每个成员
   容器里的执行内核。
2. DSH 的 preset 等价于 shell 权限。社群之间只交换万象的声明式应用包，安装时在成员
   实例上重新编译；绝不交换 `agent.cordis.yml`。
3. DSH 没有独立评判器、持久调度、离线审批。审查闸门、制作状态机、定时器、审批队列
   都是万象自己的插件。

## 4. 旅程与四个地方

```
收到链接 → 登录 → 「想造什么」 → 访谈（说明书长出来）→ 开始制作（进度卡 + 证据）
   → 验收（用自己的案例打分）→ 教它（改说明书 → 重跑 → 对比 → 接受 / 回滚）
   → 日常使用（一键跑 / 定时 / 给资料 / 审批）
   → 卡壳：找人帮忙（AI → 工作人员 → 远程接管）
   → 分享到社群（脱敏应用卡）→ 别人拿来用 / 二次开发 → 改进回馈给原作者
```

- **我的应用**：侧栏列表 + 首屏卡片。一个应用 = 一个 DSH workspace。
- **应用主页**：运行、最近产出、待你批准、教它、版本、定时、资料、分享、求助。
- **对话**：访谈与制作都在同一个对话里，DSH 原生会话。
- **社群**：市集、求助、课程。中央服务自己的网页；DSH 里只留一个抽屉入口。

## 5. 方向一：引导式访谈 → 说明书

- 每轮三拍：回读 → 写进第几节 → 只问一个问题，带 3～4 个写明后果的选项。
- 说明书 9 节：目标、输入、代表案例、规则与偏好、产出、边界与禁区、运行方式、
  验收标准、判断沉淀。每节标「你说的 / 我推断的 / 还没聊到」。
- 访谈引擎是可分支的访谈图：代码决定唯一下一问，模型负责措辞与选项；每节有必问、
  追问、材料触发三类探针。第 2～3 轮就要真实材料，案例从材料里长出来。
- 四个必填节（目标、输入、产出、验收）用户确认 + ≥1 真实材料 + ≥3 案例即可开工。
- 从社群拿来的应用走差异访谈：只问「你和 TA 不一样的地方」。

## 6. 方向二：制作、验收、教它、运行

- 制作卡五步：理解 → 搭建 → 自测 → 审查 → 交付。编译器把说明书落成应用包；每个
  验收案例开全新运行会话自测；独立审查员（另一个模型）对照验收标准打分；不达标喂给
  调教引擎修订手册、只重跑失败案例，最多三轮；三轮不过直接「请社群帮忙」。
- 编排是万象自己的持久状态机，容器重启可续跑；三个角色（制作员 / 运行员 / 审查员）
  都是普通 DSH 会话，各用各的模型。制作与自测期外部动作一律影子运行。
- 验收只做判断题：对 / 不对（说哪里不对）/ 勉强。
- 教它：自然语言反馈 → 只修订被指到的条目 → 铸新版本 → 重跑该案例 → 左右对比 →
  接受 / 回滚。版本账本追加即版本。
- 运行：一键运行、定时（宕机只补最新一次）、给资料、最近产出、参数。说明书第 7 节
  交付时自动写入定时器。
- 审批是万象自己的答复器：能展示「它想给谁发、内容是什么」；允许 / 这次不 / 以后都
  允许这类；无人值守撞到审批时产出「待你批准」卡并推通知，不挂起。

## 7. 方向三：社群

- 求助三级：AI 客服 → 工作人员（支持台）→ 远程接管（代改说明书 → 代跑测试 →
  接管对话）。接管在代理层实现，每条消息标工作人员并写审计，成员收回即撤销令牌。
- 应用包是社群唯一交换物：`app.yml`（AppSpec v2）+ `prd.md` + `skills/*/SKILL.md` +
  `cases/`（脱敏）+ `manifest.yml`（作者、版本、血缘、连接器）。安装时重新编译。
- 市集按场景浏览；拿来用 = 推包到成员实例 + 差异访谈；改进可回馈原作者一键合并。

## 8. 「有用」的最低定义

- 面向一项真实且会重复发生的工作。
- 至少一份真实材料；≥3 个案例完成验收，其中 ≥1 个边界案例。
- 连续 3 次真实运行结果由成员确认可接受。
- 所有外部写入、发送、删除、付款等动作都有明确审批策略。
- 运行过程可追溯，失败时能说明下一步。
- 成员知道如何运行、停止、教它、求助。

## 9. 分期

- **第 0 期（1 周）定局**：合并仓库、钉 DSH 版本、跑通启动、补齐 DSH 文档、本文档。
- **第 1 期（4～6 周）cohort MVP**：托管、访谈 v2、制作 v1、教它、我的应用 + 应用主页、
  审批与定时、求助（代改 / 代跑）。10～20 名成员，1～2 类场景。
- **第 2 期（4 周）社群闭环**：应用包、注册表、市集、拿来用、差异访谈、回馈、接管对话、
  第一个真实数据源、课程。
- **第 3 期**：本地桌面包、更多连接器、市集运营。

## 10. 风险
- DSH 每天一个 alpha，接口会漂：钉版本，升级前全量回归。
- 审查员是模型评模型：换模型家族，案例期望由用户写，验收最终由用户判断。
- 托管意味着成员资料在我们服务器上：隐私声明、容器隔离、审计；第 3 期给本地选项。
